# OFTP2 ERP Acknowledgements Channel

The OFTP2 ERP Acknowledgements sender channel is an optional channel that consolidates End-to-End Response \(ERP\) messages from all sources in your OFTP integration into a single collection point.

When deployed, the channel handles three types of ERP events:

-   EERP and NERP commands delivered by a trading partner in a dedicated asynchronous session
-   EERP and NERP messages generated by the SAP system after successfully receiving a file from a partner
-   EERP and NERP notifications returned by the trading partner within the same session in which the SAP system sent a file \(synchronous delivery confirmations\)

Without this channel, the adapter processes file transfers normally. Synchronous ERPs are delivered to the receiver integration flow, and SAP-generated ERPs are sent to the partner without being forwarded. If a trading partner opens a dedicated session to deliver an asynchronous EERP or NERP and no ERP Acknowledgements channel is deployed, the adapter terminates that session with an error.

When the channel is deployed, it adds a forwarding path for all three ERP types without changing the existing behavior: synchronous ERPs continue to be delivered to the receiver integration flow and are additionally forwarded to the channel; SAP-generated ERPs are forwarded to the channel after being sent to the partner; and asynchronous ERPs from the partner are routed to the channel instead of terminating the session.



<a name="loio198398865f62421785c22816c2a25b1d__prerequisites"/>

## Prerequisites

To receive ERPs from a partner, configure the following two sender channels for that partner:

-   A standard OFTP2 sender channel, which accepts and authenticates the incoming session. For more information, see [Configure the OFTP Sender Adapter](configure-the-oftp-sender-adapter-3420f2a.md).
-   An OFTP2 ERP Acknowledgements sender channel, which collects the ERP and delivers it to your integration flow.

> ### Note:  
> The partner connects through the standard OFTP2 channel. The ERP Acknowledgements channel then collects the acknowledgements received on that connection, regardless of which integration flow sent the original file.

> ### Restriction:  
> Only one ERP Acknowledgements channel can be active per runtime node at any time. If you deploy a second integration flow that contains such a channel while one is already running, the second integration flow fails to start.



<a name="loio198398865f62421785c22816c2a25b1d__when-to-deploy"/>

## When to Deploy the ERP Acknowledgements Channel


<dl>
<dt><b>

Receiving asynchronous ERPs from a trading partner \(Required\)

</b></dt>
<dd>

When a trading partner delivers an EERP or NERP in a separate OFTP session after a file transfer has completed, the adapter expects an ERP Acknowledgements channel to be deployed. If none is present, the adapter terminates the partner's session with an error. Deploy the ERP Acknowledgements channel before the partner begins sending asynchronous ERPs. See: [Asynchronous ERPs from the Trading Partner](oftp2-erp-acknowledgements-channel-1983988.md#loio198398865f62421785c22816c2a25b1d__async-erps).



</dd><dt><b>

Monitoring SAP-generated ERPs \(Optional\)

</b></dt>
<dd>

When the SAP system receives a file from a partner, it generates an EERP or NERP as an acknowledgement. If an ERP Acknowledgements channel is deployed, a copy is forwarded to it. If no channel is deployed, the generated ERP is silently discarded and the file-receive flow completes normally. See: [SAP-Generated ERPs](oftp2-erp-acknowledgements-channel-1983988.md#loio198398865f62421785c22816c2a25b1d__sap-generated-erps).



</dd><dt><b>

Consolidating synchronous delivery confirmations \(Optional\)

</b></dt>
<dd>

When the SAP system sends a file to a trading partner and the partner returns an EERP or NERP within the same session, the confirmation is always delivered to the receiver integration flow. If an ERP Acknowledgements channel is deployed, an additional copy is forwarded to it. If no channel is deployed, behavior is unchanged. See: [Synchronous ERPs from the Trading Partner](oftp2-erp-acknowledgements-channel-1983988.md#loio198398865f62421785c22816c2a25b1d__synchronous-erps).



</dd>
</dl>

## Asynchronous ERPs from the Trading Partner

A trading partner delivers an asynchronous ERP by opening a new OFTP session to the standard OFTP2 sender channel. The partner sends an EERP or NERP command, and the adapter routes it to the ERP Acknowledgements channel.

An asynchronous ERP is processed only when both the standard OFTP2 sender channel and the ERP Acknowledgements channel are configured and deployed for the same partner.

> ### Caution:  
> If no ERP Acknowledgements channel is deployed, the adapter terminates the partner's session with an error and the partner receives an error response. Deploy the ERP Acknowledgements channel before the partner begins sending asynchronous ERPs.



### Correlating Asynchronous ERPs

The adapter correlates each asynchronous ERP back to the original outbound file transfer. When a match is found, the `CorrelationMPLID` element in the delivery report XML is set to the Message Processing Log \(MPL\) ID of the integration flow execution that sent the file.

If the adapter can't find a matching correlation, the behavior is governed by the `Unexpected ERP Handling` property of the ERP Acknowledgements channel:

Each asynchronous ERP is delivered as a separate message. The `ERPSource` field identifies the origin of the acknowledgement. The value `Partner:<partnerId>` indicates an ERP received from the trading partner. The same value appears in both the XML body and the message header `SAP_OFTP_Inbound_ERP_Source`.

The following example shows the delivery report format:

```
<?xml version='1.0' encoding='UTF-8'?>
<ERPDeliveryReportsPackage>
  <PackageInfo>
    <CreatedOn>2026-08-31T10:21:14.811493454</CreatedOn>
  </PackageInfo>
  <ERPDeliveryReport>
    <CorrelationMPLID>AGqVVZf3FnToF4hU8Y5wd3_a7NYp</CorrelationMPLID>
    <ERPSource>Partner:O0000PARTNERTEST00</ERPSource>
    <EERP>
      <EERPCMD>E</EERPCMD>
      <EERPDSN>outfile</EERPDSN>
      <EERPRSV1></EERPRSV1>
      <EERPDATE>20260831</EERPDATE>
      <EERPTIME>1021120158</EERPTIME>
      <EERPUSER></EERPUSER>
      <EERPDEST>O0000PARTNERTEST00</EERPDEST>
      <EERPORIG>O0000EICTEST00000</EERPORIG>
      <EERPHSHL>0</EERPHSHL>
      <EERPHSH></EERPHSH>
      <EERPSIGL>0</EERPSIGL>
      <EERPSIG></EERPSIG>
    </EERP>
  </ERPDeliveryReport>
</ERPDeliveryReportsPackage>
```

> ### Note:  
> A negative response uses the same format, with a `<NERP>` element in place of `<EERP>`.



<a name="loio198398865f62421785c22816c2a25b1d__sap-generated-erps"/>

## SAP-Generated ERPs

When the SAP system receives a file from a trading partner, it generates an EERP or NERP acknowledgement and sends it to the partner. If an ERP Acknowledgements channel is deployed, the adapter simultaneously forwards a copy to that channel.

This forwarding is best-effort. A failure to forward does not interrupt the file-receive flow. If no ERP Acknowledgements channel is deployed, the generated ERP is not forwarded and processing continues normally.

The `ERPSource` field is set to `SAP:<senderChannelName>`, where`senderChannelName` identifies the sender channel on which the file was received. The value appears in both the XML body and the message header `SAP_OFTP_Inbound_ERP_Source`. The delivery report uses the same XML format described in [Correlating Asynchronous ERPs](oftp2-erp-acknowledgements-channel-1983988.md#loio198398865f62421785c22816c2a25b1d__correlating).



<a name="loio198398865f62421785c22816c2a25b1d__synchronous-erps"/>

## Synchronous ERPs from the Trading Partner

When the SAP system sends a file to a trading partner, the partner may return an EERP or NERP within the same session. This confirmation is always delivered to the receiver integration flow as a delivery report. For more information, see [Configure the OFTP Receiver Adapter](configure-the-oftp-receiver-adapter-8a6b283.md).

If an ERP Acknowledgements channel is deployed, synchronous notifications are automatically forwarded to it, ensuring that delivery outcomes are consolidated in a single, consistent stream for alerting and reconciliation.

> ### Note:  
> If no ERP Acknowledgements channel is deployed, synchronous notifications are delivered through the receiver channel as before. Deploying the ERP Acknowledgements channel is an optional enhancement that does not change existing behavior.

Both the receiver integration flow and the ERP Acknowledgements channel receive the delivery report independently. Deploying the channel does not remove the ERP from the receiver integration flow.

This forwarding is best-effort. If forwarding fails, the error is logged and the receiver integration flow is not affected.

Each synchronous notification includes the following information:

-   Whether the outcome was positive \(EERP\) or negative \(NERP\), and for negative responses, the reason
-   The file that the notification refers to, correlated back to the original transfer
-   The origin of the notification

The message headers set on the forwarded message are `SAP_OFTP_Inbound_Own_Id` and `SAP_OFTP_Inbound_Partner_Id`.

<a name="loio198398865f62421785c22816c2a25b1d__constraints"/>

## Limitations


<dl>
<dt><b>

One channel per runtime node

</b></dt>
<dd>

Only one ERP Acknowledgements channel may be active per runtime node at any time. If you deploy a second integration flow that contains such a channel while one is already running, the second integration flow fails to start with an error. Undeploy the running integration flow before deploying the replacement.



</dd><dt><b>

Session error when no channel is deployed for asynchronous ERPs

</b></dt>
<dd>

If a trading partner opens a session and delivers an EERP or NERP command, and no ERP Acknowledgements channel is deployed, the adapter terminates the session with an error. The partner's ERP is not processed.



</dd><dt><b>

No impact on file-transfer flows when the channel is absent

</b></dt>
<dd>

SAP-generated ERPs and synchronous partner ERPs are handled on a best-effort basis. The absence of the ERP Acknowledgements channel does not cause file transfers to fail.



</dd>
</dl>
